3. Getting started
==================
Wait for the router and frontend:
  kubectl -n {{ .Release.Namespace }} wait --for=condition=Available \
    deployment/{{ include "openreplay.fullname" . }}-router --timeout=10m
  kubectl -n {{ .Release.Namespace }} wait --for=condition=Available \
    deployment/{{ include "openreplay.componentName" (dict "root" . "component" "frontend") }} --timeout=10m

Confirm the health endpoint:
  kubectl -n {{ .Release.Namespace }} run openreplay-check --rm -i --restart=Never \
    --image=curlimages/curl -- http://{{ include "openreplay.fullname" . }}:{{ .Values.service.port }}/healthz

Install tracker 19.x on the application being observed. Backend 1.28 and
Assist 11.x must be upgraded together with the tracker compatibility contract.

7. Troubleshooting
==================
All component status:
  kubectl -n {{ .Release.Namespace }} get pods \
    -l app.kubernetes.io/instance={{ .Release.Name }} -o wide

Router logs:
  kubectl -n {{ .Release.Namespace }} logs \
    deployment/{{ include "openreplay.fullname" . }}-router

Current and previous logs for a component:
  kubectl -n {{ .Release.Namespace }} logs \
    deployment/{{ include "openreplay.componentName" (dict "root" . "component" "api") }}
  kubectl -n {{ .Release.Namespace }} logs --previous \
    deployment/{{ include "openreplay.componentName" (dict "root" . "component" "api") }}

Pending scratch PVCs mean the cluster probably lacks an RWX storage class.
Unschedulable application pods on ARM are expected: upstream publishes amd64
only. Router 502 responses indicate a disabled or unavailable target component.
Check the migration Job before investigating repeated component restarts.
