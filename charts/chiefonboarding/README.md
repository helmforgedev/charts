# ChiefOnboarding Helm Chart

Deploy [ChiefOnboarding](https://chiefonboarding.com) on Kubernetes using the
official
[chiefonboarding/chiefonboarding](https://hub.docker.com/r/chiefonboarding/chiefonboarding)
container image.

ChiefOnboarding is an employee onboarding automation platform for preboarding,
task management, and new hire workflows.

## Features

- **Employee onboarding automation** - preboarding, task management, workflows
- **Django-based** - single application container
- **PostgreSQL backend** - bundled subchart or external database
- **Auto-generated secrets** - Django `SECRET_KEY` can be generated by the chart
- **Database wait initContainer** - waits for PostgreSQL before app startup
- **Ingress support** - TLS with cert-manager, traefik, or nginx
- **Immutable image** - official 2.5.0 image pinned by manifest digest
- **Secure pod baseline** - seccomp, dropped capabilities, no privilege escalation,
  and no Kubernetes API token
- **Ingress isolation** - NetworkPolicy enabled by default

## Installation

**HTTPS repository:**

```bash
helm repo add helmforge https://repo.helmforge.dev
helm repo update
helm install chiefonboarding helmforge/chiefonboarding -f values.yaml
```

**OCI registry:**

```bash
helm install chiefonboarding oci://ghcr.io/helmforgedev/helm/chiefonboarding -f values.yaml
```

## Basic Example

```yaml
# values.yaml - bundled PostgreSQL
chiefonboarding:
  baseUrl: http://localhost:8000
  allowedHosts:
    - localhost
    - 127.0.0.1
  secretKey: "replace-with-a-stable-django-secret-key"
```

After deploying, access ChiefOnboarding:

```bash
kubectl port-forward svc/<release>-chiefonboarding 8000:80
# Open http://localhost:8000
```

## External Database

```yaml
postgresql:
  enabled: false

database:
  external:
    host: postgres.example.com
    name: chiefonboarding
    username: chiefonboarding
    existingSecret: chiefonboarding-db-credentials
```

## Application and Service ports

`chiefonboarding.port` configures the real Gunicorn listener in the official
Supervisor configuration. `service.port` is the independent client-facing
cluster port and targets the named `http` container port:

```yaml
chiefonboarding:
  port: 9080

service:
  port: 8080
```

The custom-port k3d scenario sends a real HTTP request to the overridden
listener. Changing only `service.port` does not change the application process.

## Upgrading to 2.5.0

[Upstream 2.5.0](https://github.com/chiefonboarding/ChiefOnboarding/releases/tag/v2.5.0)
adds access reports and CSV exports, external user-ID backfill, pagination fixes,
and background offboarding account checks. Back up PostgreSQL and preserve the
Django secret before upgrading; startup applies the application migrations.
Update custom integration manifests for user-ID lookup before using backfill.

Presigned S3 uploads remain the upstream default. The optional
`AWS_USE_PRESIGNED_UPLOADS=False` environment variable routes uploads through the
server; account for proxy timeouts and upload limits. `AWS_CDN_URL` optionally
sets the download URL base. Configure these through
`chiefonboarding.extraEnv`, with S3 credentials from Secrets. Existing ports,
database configuration and deployment topology are unchanged.

## Ingress

```yaml
ingress:
  enabled: true
  ingressClassName: traefik
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
  hosts:
    - host: onboarding.example.com
      paths:
        - path: /
          pathType: Prefix
  tls:
    - hosts:
        - onboarding.example.com
      secretName: chiefonboarding-tls
```

The `ingressClassName` defaults to `traefik` but `nginx` or any other supported ingress class can also be used.

## Key Values

| Key | Default | Description |
|-----|---------|-------------|
| `chiefonboarding.port` | `8000` | Application port (Django) |
| `chiefonboarding.baseUrl` | `""` | Public base URL of the instance |
| `chiefonboarding.allowedHosts` | localhost and 127.0.0.1 | Django Host headers; add the public hostname |
| `chiefonboarding.secretKey` | `""` | Django secret key (auto-generated) |
| `postgresql.enabled` | `true` | Deploy PostgreSQL subchart |
| `database.external.host` | `""` | External PostgreSQL host |
| `database.external.existingSecret` | `""` | Existing database password Secret |
| `ingress.enabled` | `false` | Enable ingress |
| `service.port` | `80` | Service port |
| `image.digest` | pinned 2.5.0 digest | Immutable official image manifest |
| `serviceAccount.automountServiceAccountToken` | `false` | Mount the Kubernetes API token |
| `networkPolicy.enabled` | `true` | Isolate application ingress |

| MITRE | 100.00% |
| NSA | 75.00% |
| SOC2 | 90.00% |
| Aggregate resource score | 83.33% |

Expected follow-up hardening is operator-dependent:

- Set explicit CPU and memory requests and limits.
- Preserve the default seccomp, capability-drop, privilege-escalation, and
  service-account-token controls.
- Use existing Secrets for Django and database credentials in production.
- Configure `networkPolicy.ingressFrom` for ingress controllers outside the
  release namespace.

The upstream image runs Supervisor, Gunicorn, and Django Q as root and writes
static and process-state files during startup. Consequently, non-root execution
and a read-only root filesystem are documented compatibility exceptions. The
chart does not pretend those controls are enabled.

## Operations and troubleshooting

The generated Django secret key is retained with `lookup` and Helm's keep
policy. Back up that Secret with PostgreSQL. After rotating data inside an
externally managed application or database Secret, restart the Deployment;
Helm cannot detect data-only changes in external Secrets.

Use these first-response commands:

```bash
kubectl -n <namespace> rollout status deployment/<release>-chiefonboarding
kubectl -n <namespace> logs deployment/<release>-chiefonboarding -c wait-for-db
kubectl -n <namespace> logs deployment/<release>-chiefonboarding -c chiefonboarding
kubectl -n <namespace> get events --sort-by=.lastTimestamp
```

See the [operations guide](docs/operations.md) for backup, upgrades, Secret
rotation, NetworkPolicy, and incident evidence.
