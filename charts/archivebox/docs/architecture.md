# ArchiveBox Architecture

## Overview

ArchiveBox is a web archiving application that captures URLs into multiple
formats, including HTML, PDF, screenshots, WARC data, and media. In this chart,
the application runs as a single Kubernetes Deployment backed by one persistent
data volume.

The chart favors a simple and explicit architecture:

- One ArchiveBox pod.
- One ClusterIP service.
- One data PVC by default.
- Optional ingress for HTTP access.
- Optional external PostgreSQL server for the main index.
- Optional CronJob for S3-compatible backups.

## Runtime Components

### Deployment

The Deployment preserves the official image entrypoint and starts
`archivebox server --init 0.0.0.0:<archivebox.port>`. The server supervises the
Daphne web process, capture runner, and built-in Sonic service in the same
container. Scheduled crawls need no additional container.

The entrypoint starts as root for ownership preparation and identity selection,
then runs ArchiveBox and Chromium as a non-root user. Optional `PUID`/`PGID`
values override owner autodetection; otherwise an existing non-root collection
owner is selected, falling back to 911 for a new root-owned collection. A
non-root `securityContext.runAsUser` uses that actual identity instead and must
already have writable data and runtime paths.

The deployment strategy is `Recreate`. This prevents two ArchiveBox pods from
sharing ownership of the runtime and snapshot directory during rollouts, with
either SQLite or PostgreSQL.

### Data Volume

The `data` volume is mounted at `/data`. With persistence enabled, it uses a
PersistentVolumeClaim. With persistence disabled, it falls back to `emptyDir`
for ephemeral testing.

The volume remains required with either database backend and contains:

- SQLite main database when the default backend is selected.
- Collection configuration and identity.
- Personas and browser profiles.
- Captured files and local search indexes.
- Snapshot artifacts generated by Chromium and other extractors.

Only the main SQL index moves to PostgreSQL. PostgreSQL credentials, server
provisioning, availability, and database backup are separate from the data PVC.
For SQLite, prefer fast local/block-backed storage for the main data directory;
bulky archive content may use a separate supported mount.

Writable runtime state also exists under `/opt/archivebox`, `/tmp/archivebox`,
and `/home/archivebox`. Do not make the container root filesystem read-only
without preparing all required paths.

### Chromium Shared Memory

ArchiveBox uses browser tooling for full page capture. The chart mounts
`/dev/shm` as a memory-backed `emptyDir` with a `1Gi` size limit to provide
shared memory for Chromium.

### Service and Ingress

The Service exposes the pod internally using the configured `service.port`.
Ingress is optional. When enabled, hosts and TLS are provided through
`ingress.hosts` and `ingress.tls`.

The default ingress class value is `traefik`, matching the HelmForge local test
cluster and chart documentation.

`archivebox.baseUrl` supplies upstream `BASE_URL`. When empty, the chart infers
the canonical URL from the first ingress host and a matching TLS entry. Without
ingress, it defaults to `http://archivebox.localhost:<archivebox.port>`.
Configure an explicit URL when another proxy or external port is used.

In `auto` security mode, public hostnames use single-domain replay without
JavaScript, while local `.localhost` hostnames use isolated subdomains. To
serve full JavaScript replay publicly, explicitly choose
`safe-subdomains-fullreplay`, set the base URL, and route both the base host and
`*.base-host` to the same Service with matching DNS and certificates. Admin,
public browsing, API, and individual snapshots use distinct subdomains.
The chart does not provision wildcard DNS or certificates for this mode.

## Configuration Flow

ArchiveBox settings are mapped from Helm values into environment variables:

| Value | Environment variable | Purpose |
| --- | --- | --- |
| `archivebox.baseUrl` | `BASE_URL` | Canonical public URL, with chart inference when empty |
| `archivebox.serverSecurityMode` | `SERVER_SECURITY_MODE` | Replay and control-plane isolation |
| `archivebox.allowedHosts` | `ALLOWED_HOSTS` | Advanced accepted-host override |
| `archivebox.publicIndex` | `PUBLIC_INDEX` | Public index visibility |
| `archivebox.publicAddPage` | `PUBLIC_ADD_VIEW` | Anonymous URL submission, disabled by default |
| `archivebox.puid` / `archivebox.pgid` | `PUID` / `PGID` | Docker entrypoint identity selection |
| `archivebox.searchBackendEngine` | `SEARCH_BACKEND_ENGINE` | Search backend |
| `archivebox.mediaMaxSize` | `MEDIA_MAX_SIZE` | Maximum media download size |
| `archivebox.timeout` | `TIMEOUT` | Per-URL archive timeout |
| `archivebox.timezone` | `TZ` | Runtime timezone |
| `externalDatabase.enabled` | `ARCHIVEBOX_DATABASE_ENGINE=postgres` | Select external PostgreSQL |
| `externalDatabase.host` / `port` | `ARCHIVEBOX_DATABASE_HOST` / `PORT` | PostgreSQL endpoint |
| `externalDatabase.name` / `user` | `ARCHIVEBOX_DATABASE_NAME` / `USER` | PostgreSQL database and role |
| `externalDatabase.existingSecret` | `ARCHIVEBOX_DATABASE_PASSWORD` | Password loaded from the configured Secret key |

Admin credentials are loaded from a Kubernetes Secret. The chart can create that
Secret or reference an existing Secret. PostgreSQL passwords must come from an
existing Secret. Snapshot visibility uses per-snapshot `PERMISSIONS`, configured
through the UI; the removed `PUBLIC_SNAPSHOTS` global toggle is not emitted.

## Backup Flow

When backups are enabled, the CronJob executes in two phases:

1. The init container creates a compressed tar archive from `/data`.
2. The upload container sends that archive to the configured S3-compatible
   bucket and prefix.

Both containers share an `emptyDir` work directory. The backup job mounts the
ArchiveBox PVC read-only to avoid modifying application data. Read-only access
does not make a live tar archive transaction-consistent. The CronJob does not
back up external PostgreSQL. See [the backup guide](backup.md).

## Scaling Boundaries

This chart does not support horizontal application scaling. PostgreSQL does not
change the single-owner archive/runtime model. To increase capacity,
scale vertically by increasing CPU, memory, storage performance, and storage
size.

## Failure Domains

Primary failure domains:

- PVC exhaustion from large snapshot volume.
- Chromium memory pressure during complex captures.
- Canonical URL, ingress, TLS, or replay security-mode mismatch.
- PostgreSQL connectivity or credentials errors when the external backend is used.
- Backup jobs failing because credentials, endpoint, or bucket policy are
  incorrect.

Use Kubernetes events, pod logs, PVC metrics, and CronJob job history as the
first troubleshooting points.
