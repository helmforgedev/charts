3. Getting started
==================

Attic uses signed JWT tokens. Keep the root token private and issue narrow,
short-lived tokens for CI users.

Wait for the API:

  kubectl -n {{ .Release.Namespace }} rollout status deployment/{{ include "attic.fullname" . }} --timeout=180s

Generate a cache-scoped token from an administrative environment that has the
signing key:

  atticadm make-token --sub ci --validity '30 days' --pull ci --push ci --create-cache ci

Configure a client and create the cache:

  attic login helmforge {{ .Values.config.apiEndpoint }} TOKEN
  attic cache create ci
  attic use ci

Push a Nix closure:

  attic push ci ./result

7. Troubleshooting
==================

Show pod state and recent events:

  kubectl -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }} -o wide
  kubectl -n {{ .Release.Namespace }} get events --sort-by=.lastTimestamp

Show API logs, including a previous crashed process:

  kubectl -n {{ .Release.Namespace }} logs deployment/{{ include "attic.fullname" . }} -c attic --tail=200
  kubectl -n {{ .Release.Namespace }} logs deployment/{{ include "attic.fullname" . }} -c attic --previous --tail=200

Show configuration-validation logs:

  kubectl -n {{ .Release.Namespace }} logs deployment/{{ include "attic.fullname" . }} -c check-config --tail=200

Distributed-mode diagnostics:

  kubectl -n {{ .Release.Namespace }} get jobs -l app.kubernetes.io/component=migration
  kubectl -n {{ .Release.Namespace }} logs deployment/{{ include "attic.fullname" . }}-gc --tail=200

Common causes:

- HTTP 400: the Host header is missing from config.allowedHosts.
- Push timeout: increase proxy body-size and read/write timeouts.
- PostgreSQL failure: verify the database-url key in the existing Secret.
- S3 redirect or download failure: make the configured endpoint reachable by clients.
- Permission denied under /data: verify PVC ownership and fsGroup support.
- Existing tokens rejected: confirm that JWT key, issuer and audience did not change.
- Low deduplication after an upgrade: check whether chunking parameters changed.

The TCP probes only confirm that the listener is open. They do not verify
PostgreSQL or S3 availability; use logs and a real cache push/pull for that.
