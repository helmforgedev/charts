# Production Guide

MediKeep processes personal health information. Treat PostgreSQL, uploads,
generated backups, application Secrets, logs, snapshots, and support bundles as
sensitive data subject to the same access and retention controls.

## First Login And Secrets

Set a strong initial administrator password before the first startup and rotate
it after login. Supply `SECRET_KEY` and the initial password through
`secrets.existingSecret`; supply database credentials through
`postgresql.auth.existingSecret` or `database.external.existingSecret`.
The bundled PostgreSQL Secret must contain `postgres-password` and
`user-password`, unless the corresponding key names are overridden.

Keep `app.debug=false` and `app.enableApiDocs=false` unless API documentation is
protected by an authenticated internal route.

## Persistence And Backups

The uploads PVC and PostgreSQL are independent data domains. MediKeep's backups
PVC stores files generated by the application, but enabling it does not copy
those files off-cluster. A recoverable plan must export database backups and
the uploads and backups volumes to separate storage, then test restoration.

Application logs are ephemeral by default because they can contain health-data
context. Enable persistent logs only with explicit encryption, access, and
retention policies.

## Scaling Boundary

Keep `replicaCount=1`. The application writes uploads and generated backups to
`ReadWriteOnce` volumes and the chart intentionally uses a `Recreate` strategy.
The PodDisruptionBudget protects voluntary maintenance but does not provide high
availability.

## Exposure

Terminate TLS at Ingress or Gateway API, restrict the route to intended users,
and enable NetworkPolicy. If egress is restricted further, retain DNS,
PostgreSQL, identity-provider, and any upstream synchronization destinations in
the allowlist. The chart automatically selects bundled PostgreSQL pods; set
`networkPolicy.egress.databaseTo` to explicit peers when using an external
database.
