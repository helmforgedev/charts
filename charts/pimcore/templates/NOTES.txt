3. Getting started
==================

The official pimcore/pimcore image is a PHP runtime, not a complete project
image. This chart handles that boundary explicitly.

Evaluation workflow:

  1. Keep project.bootstrap.enabled=true and project.persistence.enabled=true.
  2. Wait until the project skeleton is present:

     kubectl exec -n {{ include "pimcore.namespace" . }} deploy/{{ include "pimcore.fullname" . }} -c php-fpm -- test -f bin/console

  3. Register this instance with Pimcore.
  4. Store the matching product key, instance identifier, and encryption
     secret in a Kubernetes Secret.
  5. Upgrade with auth.existingSecret and install.enabled=true.
  6. Disable install.enabled after the installer Job succeeds.
  7. Enable worker.enabled and maintenance.enabled.

Production workflow:

  1. Build an immutable project image FROM {{ include "pimcore.runtimeImage" . }}.
  2. Include composer.lock, vendor, project configuration, and bin/console.
  3. Set image.repository and image.tag to that immutable image.
  4. Set project.bootstrap.enabled=false.
  5. Set project.persistence.enabled=false.
  6. Keep user assets on RWX storage or an external object store.
  7. Run the installer only for a new database.
  8. Enable workers and maintenance after schema initialization.

  kubectl get secret -n {{ include "pimcore.namespace" . }} {{ include "pimcore.secretName" . }} -o jsonpath="{.data.{{ .Values.auth.adminPasswordKey }}}" | base64 -d

Never reuse one product key across independent Pimcore instances. The product
key, instance identifier, and encryption secret must be generated as one
matching registration set.

7. Troubleshooting
==================

Inspect pods:
  kubectl get pods -n {{ include "pimcore.namespace" . }} -o wide

Describe the web pod:
  kubectl describe pod -n {{ include "pimcore.namespace" . }} -l app.kubernetes.io/component=web

PHP-FPM logs:
  kubectl logs -n {{ include "pimcore.namespace" . }} deploy/{{ include "pimcore.fullname" . }} -c php-fpm

nginx logs:
  kubectl logs -n {{ include "pimcore.namespace" . }} deploy/{{ include "pimcore.fullname" . }} -c nginx

Bootstrap logs:
  kubectl logs -n {{ include "pimcore.namespace" . }} deploy/{{ include "pimcore.fullname" . }} -c prepare-project

Worker logs:
  kubectl logs -n {{ include "pimcore.namespace" . }} -l app.kubernetes.io/component=worker --all-containers

Recent events:
  kubectl get events -n {{ include "pimcore.namespace" . }} --sort-by=.lastTimestamp

Common causes:

  - Product registration errors mean the three registration values do not
    match this instance.
  - Installer failures usually require checking MariaDB collation, credentials,
    and product registration before retrying.
  - A 404 before installation is expected in runtime/bootstrap mode; healthz
    and readyz still verify nginx and PHP-FPM.
  - Composer bootstrap requires outbound HTTPS and should not be used for
    production rollouts.
  - Multi-replica web deployments require immutable project images and shared
    asset storage.
  - Workers must start only after the database is installed.
